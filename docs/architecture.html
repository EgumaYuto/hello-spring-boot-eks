ECS から EKS へ — Fargate で動かすしくみ

同じ Spring Boot アプリを、ECS Service ではなく EKS + Fargate に載せ替えたときに「何が」「どう」動いているか。リクエストの流れ・EKSの二面構造・IRSA認証・Terraformとデプロイの分担を図で追う学習ノート。

リクエストが届くまでの流れ

ブラウザから http://<ALBのDNS名>/ を叩いてから、Spring Boot が Hello World! を返すまでに、リクエストは public → private サブネットの境界を1回だけ越えて Pod にたどり着きます。

EKS の二面構造と Fargate

EKS は コントロールプレーン（AWSが管理する頭脳）と データプレーン（Podが実際に動く場所）に分かれます。Fargate ではデータプレーンに EC2ノードが存在せず、Pod 1つごとに専用のマイクロVMが起動します。

Fargate 特有の罠 — CoreDNS

クラスタDNSの CoreDNS は既定で eks.amazonaws.com/compute-type: ec2 という注釈が付き、EC2ノードにしか乗りません。今回はノードが1台も無いので、放置すると CoreDNS が永遠に Pending → 名前解決不能 → Pod は Aurora のエンドポイント名すら引けず接続失敗。だから deploy.sh のステップ2でこの注釈を外し、Fargate に乗せ直します。

3

Pod が AWS 権限を得るしくみ (IRSA / OIDC)

解きたい問題は「静的なアクセスキーを持たせずに、ALB Controller の Pod にどうやって『ALBを作る』権限を渡すか」。答えが IRSAで、Pod の ServiceAccount と IAM ロールを OIDC の信頼で結びます。

これは ECS の Task Role に相当しますが、EKS では「ServiceAccount ↔ IAMロール」を OIDCフェデレーションで結ぶのが違いです。今回アプリ本体はDB接続にAWS権限が不要なので IRSA を使わず K8s Secret で済ませ、ALB Controller だけが IRSA を使います。

4

Terraform とデプロイの分担

Terraform は AWS リソースだけを管理し、クラスタ内の操作（kubectl / helm）は deploy.sh に集約しています。こうすると Terraform の kubernetes/helm プロバイダの「クラスタを作る前に接続する」鶏卵問題を避けられ、各コマンドが1つずつ見えて学習向きです。

シークレットの流れ

DBパスワードは Terraform が生成し、人間が知らないまま Secrets Manager を中継して Pod に届きます。
