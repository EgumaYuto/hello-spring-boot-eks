local と EKS — 同じアプリ、違うエッジ

同じ Spring Boot アプリを、①ローカルの kind クラスタ（AWS費用ゼロ）と、②AWS の EKS + Fargate で動かしたときの構成図。中央の Deployment / Service / Ingress / probe / Flyway はまったく同じで、外周（公開・DB・イメージ・Secret）だけが差し替わる、という対応関係を図で追います。

kind (Docker) nginx Ingress EKS on Fargate ALB Controller Aurora Serverless v2
1

共通の中心と、差し替わる外周

両環境は「K8s の中身は共通・エッジだけ違う」という設計です。Deployment / Service / Ingress / readiness·liveness probe / 起動時の initContainer と Flyway マイグレーションは、ローカルでも AWS でも同じ動きをします。違うのは次の 4 点だけです。

役割ローカル (local/manifests)EKS (k8s + infra)
公開nginx Ingress → http://localhost/ALB Ingress（LB Controller が自動生成）
DBクラスタ内 MySQL Pod（emptyDir）Aurora Serverless v2（別サブネット）
Secret静的な Secret（docker-compose と同値）Secrets Manager → deploy.sh が生成
イメージkind load で直接投入（レジストリ無し）ECR に push → Fargate が pull
2

ローカル構成 — kind (Kubernetes in Docker)

Docker コンテナ 1 つが Kubernetes ノードになります。kind の extraPortMappings でホスト Mac の 80/443 をノードに通し、nginx Ingress コントローラが http://localhost/ で受けます。DB も同じクラスタ内の MySQL Pod です。

3

EKS 構成 — Fargate + ALB + Aurora

外周が AWS のマネージドサービスに置き換わります。公開は ALB（k8s/ingress.yaml を見た AWS Load Balancer Controller が自動生成）、DB は private サブネットの Aurora Serverless v2、イメージは ECR、Secret は Secrets Manager から deploy.sh が組み立てます。Pod は EC2 ノードではなく Fargate のマイクロVM上で動きます。

使い分け

普段の学習は ローカル(kind) で十分 — Kubernetes の核心（Deployment / Service / Ingress / probe / rollout / kubectl）はクラウドと同じ動きです。IRSA / ALB Controller / Fargate / Aurora といった AWS 固有の挙動を試すときだけ EKS を立てる、という運用を想定しています。

local/manifests/ ・ k8s/ ・ infra/ の実マニフェストに基づく構成図。詳しい EKS の内部（コントロールプレーン / IRSA / Terraform 分担）は architecture.html を参照。
